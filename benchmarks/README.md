# Benchmarks: langgraph-rs vs Python LangGraph

English | [简体中文](README.zh-CN.md)

This directory contains the functional and performance comparison between **langgraph-rs**
and the reference **Python LangGraph**. Results are regenerated on the machine you run them
on; do not compare absolute numbers across different machines.

## Scenarios

All engines implement the same scenario with the same node counts and iteration counts.
The measured operation is a full graph invocation (or, for `build_compile`, graph
construction + compilation). Checkpointing scenarios use a fresh thread id per run so the
saver does not accumulate unbounded history.

| Scenario | Nodes | Iterations | What it measures |
| --- | --- | --- | --- |
| `linear_10` | 10 chained nodes, `value += 1` | 1,000 | per-run orchestration overhead of a simple pipeline |
| `loop_50` | one node + conditional loop until `value == 50` | 200 | superstep/conditional-routing overhead per loop step |
| `fanout_4` | dispatch → 4 parallel workers → join | 1,000 | parallel superstep scheduling + channel merging of 4 writes |
| `checkpoint_5` | 5 chained nodes with an in-memory checkpointer, new thread per run | 200 | checkpoint write/read overhead per superstep |
| `build_compile` | 10-node graph definition | 500 | builder + validation + compile cost |
| `scale_005` … `scale_100` | linear chains of 5/10/25/50/100 nodes | 1,000 → 100 | how orchestration cost grows with graph size |
| `mt_8x_linear_10` | 8 threads run the `linear_10` graph concurrently | 1,000 total | threaded throughput (native: one shared graph; Python: one graph per thread) |
| `mem_linear_10`, `mem_loop_50` | same graphs as `linear_10` / `loop_50` | 200 | allocation high-water mark (and, for Rust, allocation churn per op) |

Implementation:

- Rust native: [`benches/bench_rust.rs`](../benches/bench_rust.rs), run with
  `cargo bench --bench bench_rust`.
- Python LangGraph: [`python/benchmarks/bench.py`](../python/benchmarks/bench.py)
  (`--engine langgraph`), against LangGraph 1.2.x.
- Rust via Python bindings: the same script with `--engine binding`, importing the PyO3
  extension module (`cargo build --release --features python`).
- Scaling runs use `nodes + 10` as the recursion limit on every engine so 50/100-node
  chains do not trip the default limit of 25.

## Running

```bash
# One-shot: build artefacts, run all three engines, write results
python benchmarks/run.py

# Re-run only the measurements with existing artefacts
python benchmarks/run.py --skip-build
```

The runner writes:

- [`RESULTS.md`](RESULTS.md) — generated comparison table and environment information;
- [`results/latest.json`](results/latest.json) — every raw record (engine, scenario,
  iterations, total ms, ns/op, ops/s).

## Methodology and caveats

- Wall-clock timing around the measured loop only; warm-up runs (10% of iterations) are
  executed first and excluded. Results are a single run — treat small differences (<10%)
  as noise.
- Python LangGraph is measured through its synchronous `invoke` entry point; no async
  event loop is used for any engine. LangGraph may still create its own task machinery
  internally.
- Checkpointing implementations differ: Python uses `MemorySaver`, Rust uses the
  `InMemorySaver` adapter over the `Checkpointer` port; both keep checkpoints in memory.
- The native Rust numbers use the release-equivalent `bench` profile; the Python binding
  numbers include Python callable dispatch (GIL acquisition per node) and dict conversion
  per superstep.
- These benchmarks measure **orchestration overhead**, not LLM latency. They contain no
  model calls, network I/O or disk I/O.
- **Threading:** `mt_8x_linear_10` runs 8 OS threads for 1,000 total invocations. The native
  engine shares one compiled graph through an `Arc`; the Python engines create one compiled
  graph per thread because LangGraph and the bindings are not documented as thread-safe
  objects. Python's GIL limits the Python engines' scaling; the scenario therefore compares
  throughput as users would actually run it.
- **Memory:** Rust numbers come from a counting global allocator in the bench binary. The
  counters are disabled during timing scenarios and enabled only for `mem_*`, where they
  report the allocation high-water mark and total allocation churn per operation. Python
  numbers use `tracemalloc` around the measured loop. `tracemalloc` only sees Python-level
  allocations, so the binding's peak is a lower bound on its real footprint; compare Rust vs
  LangGraph for a meaningful signal.
- The counting allocator adds a relaxed atomic load per allocation; treat differences below
  ~10% between runs as noise, and compare ratios between engines rather than absolute
  numbers over time.
- The functional comparison (what works, what differs) lives in
  [`features.md`](features.md).

## Results snapshot

The table below is regenerated by `python benchmarks/run.py`; see
[`RESULTS.md`](RESULTS.md) for the current numbers and environment. Typical outcome on a
modern x86-64 machine: native Rust is one to two orders of magnitude faster than Python
LangGraph for the same small graphs, while the PyO3 bindings sit between the two (they add
Python callable dispatch on every node execution).

## Behavior / performance parity

`python benchmarks/parity.py` runs the same scenarios on Python LangGraph and the
`langgraph-rs` Python bindings, compares observable results, and writes
`benchmarks/parity_results.json` plus `benchmarks/PARITY.md`.

The latest run covers 26 scenarios: linear execution, conditional branches, loops, batch,
managed values, v1/v2 streaming, messages/token streaming, Command(update/goto/PARENT), retry policies, error handling/propagation, node timeout, node cache, store round trips, SQLite/Postgres/Redis persistence, async
execution, interrupt/resume, nested subgraph interrupt/resume, `update_state`, checkpoint
history, and subgraphs. Every scenario records behavior equivalence plus per-scenario latency
for both engines. The SQLite saver runs in WAL/NORMAL mode, which brought its parity benchmark
from ~0.5x to ~20-29x versus LangGraph.

Postgres/Redis scenarios are opt-in because they need live databases:

```bash
export PARITY_POSTGRES_URL="postgresql://postgres:postgres@127.0.0.1:55001/langgraph_rs"
export PARITY_REDIS_URL="redis://127.0.0.1:55000/"
python python/benchmarks/parity.py
```

Latest remote results: Postgres ~0.9x, Redis ~2.4x versus LangGraph. `node_timeout` compares async cancellation on both engines (both fail with a timeout error). `messages_stream` notes that LangGraph captures chat-model callbacks automatically while the binding needs an explicit `langchain_callback_handler`.
